# 代码评审的关注顺序：代价与适用边界

**日期**：2026-09-06　**领域**：工程　**编号**：10/115

## 背景

任何方案都有不适用的时候，提前写清楚。这里围绕「代码评审的关注顺序」做一次整理，重点放在能直接落地的部分。

## 要点

- 先看接口契约与错误路径，再看实现细节
- 评论区分阻塞项与建议项，避免全部标为必须修改
- 把不适用条件写进文档，避免误用。

## 示例

```bash
## 阻塞
- 未处理上传失败，会静默丢数据
## 建议
- 循环内可提前返回
```

## 易错点

- 只挑格式问题会让真正风险被淹没

## 小结

代码评审的关注顺序 在代价与适用边界这一面，结论可以归纳为：把前提写清楚、把失败路径覆盖到，剩下的就是按数据调优。
